# QA Gauntlet Variability Expansion — Design Spec

**Date:** 2026-07-27
**Status:** Approved (design), pending spec review
**Author:** Claude (via brainstorming skill); scope decisions by user
**Companion doc:** [`docs/engineering/sim-capability-gap-backlog.md`](../../engineering/sim-capability-gap-backlog.md) — capabilities that could **not** be added because the sim does not model them

## Problem

The gauntlet ladder claims to stress-test the simulation across five escalating tiers, but its 24-scenario corpus exercises only **5 of the 21** scenario-policy blocks the engine supports. Thirteen engine-supported subsystems have **zero** ladder coverage despite being exercised by non-gauntlet scenarios:

| Untapped block | Non-gauntlet uses |
|---|---|
| `emcon` | 7 |
| `contactLifecycle` | 6 |
| `catalogWithdraw` | 5 |
| `datalink` | 4 |
| `logistics` | 3 |
| `jammers` | 2 |
| `speculative` | 2 |
| `spoofTracks`, `mineHazard`, `unitReadiness`, `delegation`, `missionPolicy`, `telemetry` | 1 each |

Weapons parameters are similarly under-stressed: 17 knobs exist on the `engage` block, and current scenarios sit near defaults for nearly all of them.

**Consequence:** the ladder's "escalating complexity" escalates ORBAT size and ROE, but not the systems most likely to harbour defects. The two CRITICAL engine bugs found in run `gauntlet-20260727-1455` were both in paths the ladder touched only incidentally.

## Scope

**In scope — data-only.** Scenario-policy JSON, forge recipes, and the tier matrix. No engine changes, therefore no determinism or replay-golden risk.

**Out of scope.** Weather, terrain, and other unmodelled capabilities. These require new engine subsystems and are catalogued separately in the capability-gap backlog (companion doc). This spec does not propose implementing them.

## Decisions

### 1. Fold new dimensions into the existing 5 tiers

The ladder stays a single escalating line; the tier matrix gains rows. Existing tick budgets (T1=6, T2=10, T3=16, T4=24, T5=40) are unchanged. Rejected alternatives: orthogonal stress axes layered on every tier (combinatorial run-time growth), and a parallel second ladder (roughly doubles run time, splits the narrative).

### 2. Scenario budget: 6–8 fixed per tier, forge covers combinatorics

The fixed set grows from 4 to 6–8 per tier — enough to guarantee coverage of the priority systems. Broader combinations are generated by forge mutation recipes as ephemeral candidates, promoted only when they pass the locked oracle and improve coverage. This keeps the deterministic, reviewable core small while coverage compounds across runs.

### 3. Weapons ranges: plausible **plus** deliberate boundary values

Most scenarios stay militarily credible. Each tier additionally pins one boundary condition where engine defects concentrate:

| Tier | Boundary condition |
|---|---|
| T1 | `pkKill = 1.0` exactly (always-kill path) |
| T2 | `salvoSize == maxSalvo` exactly (off-by-one on the WRA cap) |
| T3 | magazine exhaustion mid-run (`MagazineEmpty` abort under real pressure) |
| T4 | `mountOnline = false` (mount-offline abort, no magazine consumption) |
| T5 | `envelopeMin == envelopeMax` (zero-width envelope) and `pkKill = 0.0` (never-kill path) |

Outright invalid inputs (negative pk, pk > 1, salvo exceeding magazine, absurd ranges) are **excluded**: they mostly produce garbage-in failures rather than real defects, and they degrade the corpus as documentation.

### 4. Mission types are expressed by **combat domain**, not by label

`missionCode` is a free-form string — carried into `MissionTransitionRecord` for the order log, never validated or acted upon (`BalticReplayHarness.cs:416`). Mission *behaviour* therefore comes from `CombatDomain` pairings and ROE triggers, not from the label.

`missionCode` is retained as human-readable documentation, but no scenario may claim a mission type its domain configuration does not actually implement. This prevents a repeat of `BUG-t2-escort-passive-emcon-claim-unimplemented`, where a scenario advertised behaviour it did not implement.

Mission coverage achievable, by mechanism:

| Mission type | Mechanism | Available |
|---|---|---|
| Patrol | existing T1 pattern | Yes |
| Anti-air (AAW) | `CombatDomain.Air` | Yes |
| Anti-surface (ASuW) | `CombatDomain.Surface` | Yes |
| Anti-submarine (ASW) | `CombatDomain.Subsurface` | Yes |
| Air-to-surface strike | Air shooter → Surface target | Yes |
| Electronic warfare | `jammers` + `spoofTracks` (EW *effects*) | Yes |
| Land / Facility / Mine strike | `CombatDomain.{Land,Facility,Mine}` | Yes — currently zero coverage |
| **Refuelling** | — | **No** — see backlog |

Refuelling has no simulation behaviour (see companion backlog). The nearest honest substitute is the `logistics` block, which models fuel burn and joker/bingo thresholds — i.e. *fuel pressure*, never fuel transfer. Scenarios using it will be named for fuel pressure, not refuelling.

### 5. Replace EMCON detection stand-ins with the real `emcon` block

The gauntlet currently fakes EMCON via reduced `basePd`/`envMask`, because the catalog's `platform_emcon` table is empty. But a scenario-level `emcon` block exists (`{"units": {"<unitId>": {"radar": "Active|Passive"}}}`) and is used by 7 non-gauntlet scenarios — it needs no catalog data.

Switching to it closes `BUG-t2-escort-passive-emcon-claim-unimplemented` at the root and makes EMCON claims verifiable. This is a correctness fix, not merely added coverage.

## Revised tier matrix

Existing rows (mission type, platform mix, victory conditions, events, ROE) are unchanged. New rows:

| Dimension | T1 | T2 | T3 | T4 | T5 |
|---|---|---|---|---|---|
| **Combat domains** | Surface | + Air (AAW, air→surface strike) | + Subsurface (ASW) | + Land / Facility | + Mine; multiple domains concurrent |
| **EMCON** | unrestricted | real `emcon` block, passive one side | timed EMCON phases | dynamic change on detection | contested EM + deception emitters |
| **EW** | none | none | `jammers` with timed `activeFromTick` | + `spoofTracks` injects | cascading jam + spoof |
| **Logistics** | none | none | fuel burn active | joker/bingo thresholds crossed | bingo + magazine exhaustion |
| **Contact lifecycle** | none | none | classify/identify gates | + staleness thresholds | + `datalink` share-lag / organic-only |
| **Weapons boundary** | `pkKill=1.0` | `salvo==maxSalvo` | magazine exhaustion | `mountOnline=false` | zero-width envelope, `pkKill=0.0` |

Rationale for placement: EW and logistics enter at T3 because that is where subsurface units and event chains already create enough state for degradation to be observable; T1–T2 stay deliberately simple so that a T1/T2 failure remains easy to localise.

## Forge recipe additions

New mutation recipes, following the existing `recipe-catalog.yaml` schema (`id`, `dims`, `tierMin`, `preconditions`, `noveltyTags`, `forbiddenTouches`):

| Recipe | `tierMin` | Mutates |
|---|---|---|
| `emcon-real-block` | 2 | per-unit `emcon.units[].radar` Active/Passive |
| `ew-jammer-timing` | 3 | `jammers[].jamStrength`, `activeFromTick`, observer/target pairing |
| `ew-spoof-inject` | 4 | `spoofTracks[].atTick`, `contactId` |
| `logistics-fuel-pressure` | 3 | `logistics` burn rate, joker/bingo fractions |
| `contact-lifecycle-timing` | 3 | `stale/classify/identify` tick thresholds |
| `datalink-degradation` | 4 | `datalink.organicOnly`, `shareLagTicks` |
| `mine-hazard-zone` | 5 | `mineHazard` zone bounds, severity, placements |
| `weapons-boundary-probe` | 1 | the boundary conditions in Decision 3 |
| `domain-pairing-shift` | 2 | `engage.combatDomain` + unit domain mix |

The existing locked-eval contract is unchanged: recipes mutate policy JSON only, never `GauntletOracleEvaluator`, the Demo batch harness, ReplayGolden fixtures, `DelegationBridge.cs`, or the Baltic v2 golden hash.

## Verification

Each tier must satisfy the existing gates, unchanged:
- `gauntlet_oracle_eval` → `allPassed: true` at the tier's own tick budget
- Determinism: identical fingerprints for identical `(scenario, seed)` across independent runs
- Full solution suite green, test count monotonic
- Whole-corpus regression at correct per-tier budgets

Two additional checks specific to this work:
- **Dimension-coverage assertion.** A scenario claiming a dimension must demonstrably exercise it — e.g. an EW scenario must show non-zero `jamStrength` effects in its fingerprint, not merely carry a `jammers` block. This is the direct lesson of the EMCON stand-in defect.
- **Expect regeneration.** All new and modified scenarios derive `gauntlet.expect` from a real batch at the correct tier tick budget per `tools/qa-gauntlet/README-expect-regen.md`. No invented envelopes.

## Risks

**Corpus expansion may surface latent defects.** Exercising 13 previously-untested subsystems will plausibly find real bugs — that is the point, but it means this work may not land as a single clean change. Any CRITICAL-impact defect follows the established quarantine path rather than being fixed inline.

**Scenario count roughly doubles.** 6–8 per tier across 5 tiers is 30–40 fixed scenarios versus 20 today, increasing batch time proportionally. Mitigated by keeping the fixed set at the low end and delegating combinatorics to forge candidates, which run only when the forge phase runs.

**`BUG-forge-scorecard-filename-vs-policy-id` blocks promotion.** Until fixed, forge candidates must be filed as `<policy id>.policy.json` or nothing promotes. The recipes above depend on the promote loop working; this bug should be fixed before or alongside this work.
